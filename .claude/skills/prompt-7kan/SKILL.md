# 7칸 프롬프트 변환기

사용자의 한 줄 목표를 아래 7칸 틀로 바꾼다. 초보자 기준이라 설명은 쉬운 말로 짧게 한다.

## 진행 순서

1. 사용자의 한 줄 목표를 읽는다.
2. 직접 확인할 수 있는 것(운영체제, 설치 여부, 파일 존재)은 사용자에게 묻지 말고 명령으로 확인한다. 사용자는 기본적으로 **윈도우(PowerShell)** 라고 가정한다.
3. 아래 7칸을 채워서 사용자에게 보여준다.
4. 사용자가 OK 하면 그 계획대로 실행한다.
5. 검증 칸의 명령으로 성공을 확인한 뒤에만 완료라고 말한다.

## 7칸 틀

```
역할: <무슨 담당인지 한 줄>
맥락: <지금 상황 + 사용자 수준. 기본값: 개발 경험 없는 초보자, 윈도우>
입력: 목표 = <이번에 얻고 싶은 결과 한 줄>
작업:
 ① <먼저 확인할 것>
 ② <실제로 할 일. 이미 돼 있으면 건너뜀>
 ③ <②가 됐는지 다시 확인>
 ④ <사용자가 직접 해야 할 부분은 위치만 짧게 안내>
제약: 설치, 관리자 권한, 설정 파일 수정, 덮어쓰기, 삭제는 실행 전에 먼저 묻는다. 비밀번호와 키 값은 출력하지 않는다. 원본은 건드리지 않고 새 파일로 만든다.
출력: [실행한 명령 / 확인된 결과 / 바뀐 파일 / 남은 오류] 로 보고한다.
검증: <성공하면 보여야 할 것과 확인 명령>. 하나라도 실패하면 완료라고 말하지 않고, 실패한 명령·원인·다음 조치를 알려준다.
```

## 각 칸이 막아주는 실수

| 칸 | 빼먹으면 생기는 일 |
|---|---|
| 역할 | 엉뚱한 일까지 손댐 |
| 맥락 | 설명이 너무 어렵거나 너무 쉬움 |
| 입력 | 쓸데없는 질문이 쏟아짐 |
| 작업 | 순서가 꼬이고 확인을 건너뜀 |
| 제약 | 함부로 설치하고 덮어씀 |
| 출력 | 뭘 했는지 알 수 없음 |
| 검증 | "다 됐어요!" 했는데 안 돼 있음 |

## 규칙

- 검증 칸은 반드시 실제 명령으로 확인한다. 추측으로 "됐을 것"이라고 말하지 않는다.
- 사용자에게 보여주는 계획은 10줄 안팎으로 짧게 한다.
- 목표가 너무 모호하면 가장 중요한 질문 하나만 묻는다.
